The problem

The task pack is a small fictional archive: the parish records of a village called Hollowmere, 1850 to 1855. Nine plain text files under sixty lines each. A census taken on 30 March 1851 with twelve households. The mill's receipts ledger for 1852. The parish clerk's dated log of events from 1850 to 1855. Three letters: Ruth Ashby to her sister after the mill fire, Samuel Reeve to the insurers, and the Reverend Dunmore to the Archdeacon. An inventory of what the fire destroyed, with valuations. Tithe notes listing fields and occupiers. The files cross-reference each other on purpose: the ledger's payees are mostly census households, the fire in the log is the fire in the letters, the inventory total is the number the insurer argued about.

Eight tasks are seeded on the board, each with a result file name and a strict format so a verifier can score it exactly. Three of them establish base facts and carry the highest priority: T-001 counts the census (households, persons, the surname list), T-002 names the year of the mill fire and the miller at the time, T-003 totals the ledger and counts distinct payees. Each of these three tells the solver to post its fact as a finding in its thread before writing the result file, because other tasks depend on it. Three tasks consume those facts: T-004 asks which ledger payees were census households and which were outsiders, which needs T-001 and T-003; T-005 asks when the mill reopened, under whom, and how many years after the fire, which needs T-002; T-006 totals the inventory, finds the insurer's payment, and computes the shortfall. T-007 is a sixty to one hundred and twenty word chronicle assembled from the threads of T-002, T-005 and T-006, scored by ten keyword groups. T-008 asks the solver to read the board for messages of kind question, answer any it can from the materials, and list the ids it answered. The dependent tasks say, in their own text, to check the board first and to post a question in their thread if the fact they need is missing, then derive it and post it so the next solver does not have to.

The verifier compares each result file to a hidden answers file under task/verifier/, which the solvers are told never to read. Numbers and names are matched exactly after normalisation, the surname lists as sets, the chronicle by keyword coverage, and T-008 by checking which questions on the board had a finding answering them. There is a trap in the data: the census has an Alice Fenwick at Bridge End, the ledger has an unmarked Fenwick receipt, and the parish log records the burial of her brother Robert Fenwick of Netherby, the neighbouring parish. A solver that does not read carefully puts Fenwick among the outsiders.

The point of the exercise is not whether one model can read nine files. It is whether three agents that share nothing but a message board will divide the queue, publish facts before anyone asks for them, reuse each other's work instead of recomputing it, vote with reasons on what they have checked, and finish with every result passing a verifier none of them can see.

The setup

Four things run. Postgres holds every table: agents, messages, votes, tasks, config, events, handoffs, plus the server's bookkeeping. The board server is one Python process exposing fifteen MCP tools over HTTP at 127.0.0.1:8765/mcp, and it is the only thing that writes to the database. The orchestrator spawns three Claude Agent SDK sessions on claude-opus-5-5, two seconds apart, each in its own directory under agents/, with the board attached as an MCP server named civ and a per-session token in the request header so the server knows who is calling. The verifier is a Python function the server calls when a task is completed.

Each solver is told the same thing in its system prompt: claim a task, read its thread and the top findings, do the work in your own directory, post findings and questions to the thread as you go, write the result file, complete the task, cast at least one vote with a reason, claim again, and when no task is left post anything unposted and stop. It is told the materials path, that the verifier folder is off limits, that other agents' directories are off limits, and that an answer to a question is a finding posted with parent_id set to the question's id.

Some of those rules the server enforces rather than asks. One lease per session: task_claim refuses while you hold one. One vote between claims: the next claim is refused until a vote has been cast. Every post is stamped with the highest sequence number that session had read, so a message carries "I had seen the board up to here" without the agent remembering anything. Result paths must resolve inside the caller's own directory. The verifier's score reaches the agent only as a number. What stays a prompt request is judgement: which facts to post, which messages to vote on, when to ask.

How they collaborated

A fact reused instead of recomputed

T-005 needs the fire year. sol-001 did not open the parish log to find it. Its finding 21 says "Fire year 1853 per seq 10", and its completion summary cites "seq 10, seq 21". sol-002 had posted that fact at 01:06:13, twenty-two seconds before sol-001 needed it, because T-002 told it to post early. The same pattern runs through the chronicle: sol-003's T-007 summary names "seq 10, 14, 21" as its sources, which are three findings by two other agents, before it mentions the materials. The design doc's claim was that dependency would run through the board rather than through a planner, and here it did, with sequence numbers as the citations.

A one-second miss, made visible by the read stamp

T-004 needed the payee list. sol-002 searched for it at 01:06:23 and found only task descriptions. sol-003 posted the list at 01:06:24. sol-002 never re-read before it posted at 01:06:28, and the server's stamp says so: both its question 17 and its finding 18 are marked "had read to #12", one short of message 13. Nothing enforces re-reading, and the prompt only asks for a read at the start of a task, so this is the expected cost of parallelism. What matters is that the board records why the work was duplicated instead of leaving a mystery, and that the duplicate was not wasted: finding 18 is the message that explains the Fenwick trap, and it collected a vote from sol-001 for exactly that reason.

#17  (had read to #12)  "Need the T-003 ledger payee surname list; not on the board yet ..."
#13  posted 01:06:24, four seconds earlier, by sol-003
vote 01:06:48  sol-001 +1 on #18  "... the note that Fenwick counts as in-parish is useful."

A question asked, answered, and then found closed

This is the path that did not fire in the first demo run. sol-002 posted question 17 at 01:06:28. sol-003, which had read the whole board at 01:06:28 and seen it, answered at 01:06:33 with finding 19, posted in thread 4 with parent_id 17, as the prompt now requires. Both sol-002 and sol-001 voted on the answer and both reasons mention the question. Then sol-001, on T-008 at 01:06:41, asked the board for questions, got the one, saw it already carried a finding with its id as parent, and wrote "answered: none". The verifier reached the same verdict independently by the same rule. The rule had been loose the day before: any later finding in the thread counted as an answer, which would have let a task's own completion summary close an unrelated question. The review tightened it to the parent link, and the prompt was changed in the same commit so the agents would know to set it. The run shows the server, the prompt and the verifier agreeing on what an answer is.

Votes as independent verification

Twelve votes were cast, all positive, all with a reason, none on the voter's own message. The reasons are not applause. sol-001 re-added the ledger before voting on finding 13. sol-002 "independently summed the ledger to 125 shillings" before voting on the same message twenty seconds later. sol-003's vote on the census list is a cross-check against a different file: "all 7 non-Netherby payees appear in it". Three of the seven voted messages were checked by two different agents, which means the three base facts, census, fire, and ledger, each carry two independent confirmations by agents that did not produce them. The design doc's reason for mandatory vote reasons was that a score with reasons tells a successor why something mattered; here it also turned the duplicate payee derivation into a second source.

What was wasted

Two things. The payee list was derived twice, by sol-003 for T-003 and by sol-002 for T-004, because of the four-second gap and the missing re-read. And the last two findings in thread 7, by sol-001 and sol-003, overlap almost entirely: both record the burial on 17 February 1854 at age 50, both name Samuel as executor, both mention the Netherby masons. sol-003's stamp shows it had read to #22 when it posted #27, so it had not seen sol-001's #26, posted four seconds earlier. Same cause as the first miss. A re-read before posting, or a supervisor deduplicating, would have caught both, and the duplicate-finding rate is one of the four objectives supervisors will tune against once they exist.

What this does and does not show

It shows the M2 machinery working end to end on real model calls: three sessions sharing a Postgres-backed board through MCP, a claim queue that never double-leased, server-stamped read positions, mandatory votes with reasons, a verifier the agents never saw, and a dependency chain that ran through posted findings. It shows the question path and the parent-link rule working once. It shows that the whole thing costs about a dollar and a minute at this scale.

It does not show most of what the design is for. Three agents, not a hundred. One generation each: nobody came near the 80 percent handoff line, so succession, the mechanism the whole lineage story depends on, was never exercised. No supervisors, so nobody tuned a knob, deduplicated the two overlapping burial findings, or wrote a report. The tasks were small enough to finish in under a minute, so the board never grew past twenty-seven messages and the question path fired exactly once. The verifier is a lookup against an answers file, which is the easy end of the spectrum the design doc leaves open. And the agents ran as one OS user with directory isolation by convention only. The next milestones, M3 succession and M4 supervisors, are where the run stops being a worker pool and starts being a civilisation.
