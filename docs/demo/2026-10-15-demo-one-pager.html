civ M2 demo: three agents, one board, eight dependent tasks

15 October 2026 · Joshua Ang · one-pager for leadership · appendix: full minute-by-minute narrative, race timeline

Summary

We built the first three milestones of civ, a system in which many Claude agents solve a task far larger than any one context window by sharing nothing but a message board. In a 60-second live run, three Opus 5.5 solvers completed all eight tasks with a perfect verifier score for $1.01, reused each other's findings by sequence number, asked and answered one question, and verified every important fact through votes with written reasons. The run also exposed a one-second race that caused one duplicated derivation, and the board's design made that race visible after the fact.

Problem

The question is not whether a model can read nine short files. It is whether agents that never talk to each other directly will divide a queue, publish facts before they are asked for, reuse rather than recompute, and finish against a verifier none of them can read. The test corpus is a fictional 1850s parish archive. Three of the eight tasks cannot be answered without facts that other tasks establish, and the task text tells the solver to check the board first.

What we built

Postgres holds all state. A single board server exposes fifteen MCP tools (post, read, search, vote, claim, heartbeat, complete, release, handoff, alert, status, and supervisor tuning) and is the only writer. An orchestrator spawns each solver as a Claude Agent SDK session in its own directory with a per-spawn token. The server enforces the rules a prompt cannot be trusted with: one lease per agent, one vote with a reason between claims, no self-votes, claims under SELECT ... FOR UPDATE SKIP LOCKED, and a read-sequence stamp on every post that records what the author had seen. 149 tests pass, including 100 concurrent claims and an adversarial review that found and fixed ten gaps.

How they collaborated

Reuse happened by citation. Six of eight tasks were completed with zero re-derivation of upstream facts. T-005 wrote "Fire year 1853 per seq 10". T-007's chronicle was "from seq 10, 14, 21" and did no primary research. T-004 "took the census surnames from seq 9".

One race caused one duplicate. sol-002 claimed T-004 at 01:06:22 and searched the board for the ledger payees at :23. sol-003 posted them at :24. sol-002 never re-read, posted a question at :28 and its own derivation at :30, both stamped "had read to #12". sol-003 answered the question at :33, correctly and too late. The verifier still scored T-004 at 1.00, but the derivation was done twice.

Duplication was also deliberate, and cheap. Every base fact was re-derived by an agent that had not done the task, inside a vote: "Re-summed ledger_1852.txt: 14 entries total 125 shillings" (sol-001), "I independently summed the ledger and got the same 9 payees" (sol-002), "Verified against census_1851.txt" (sol-002 on sol-001's census). The one-vote quota turned idle moments into cross-checks.

What we learned

The dependency protocol "post a question, then derive it yourself" guarantees duplicate work whenever a sibling task is mid-flight, because the solver only checks the board before claiming. The fix is one line in the server: task_claim should report that T-003 is currently leased by another solver, so the claimant re-checks before deriving. Second, the end-of-loop rule "post one last finding" produced two overlapping, unrequested posts about the miller's burial; at a hundred agents that is board flood, so the rule needs a search first. Third, the question path fired but saved nothing; it will matter only when tasks take minutes rather than seconds. Fourth, this run shows one generation of three agents with a trivial verifier and no supervisors; succession (M3) and self-governance (M4) are unexercised.

Next steps

Ship the claim-time dependency hint and the search-before-posting rule, then build M3 (handoff at 80 percent of context, successor in the same directory) and M4 (supervisor rounds tuning knobs against the four objectives). Rerun with a task pack large enough that a solver cannot finish inside one context window, which is the case the whole design exists for.
